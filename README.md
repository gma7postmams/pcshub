# Promotional Content Hub

An internal web app for promotional content teams. Built with Node.js (Express), PostgreSQL and React (Vite).

## Top features

- **Ingest**: track ingest requests with an approval step, statuses, import and export.
- **Workload**: plan and follow work by day and team, with custom columns.
- **PSD Daily Plug List**: maintain the daily plug list, with Excel import.
- **Live updates**: changes other people save on the three trackers appear on your screen by themselves, without a page refresh.
- **Knowledge Base**: shared reference documents (PDF, Word, PowerPoint) with tags and a trash bin. Everyone with the page can open and download; only Admin and System Admin upload, rename or delete (adjustable per role in Administration → Roles). An item can be created with just a name and its document added later.
- **Dashboard**: workload and ingest numbers at a glance, fits the screen.
- **Admin**: users, roles and groups, dropdown lists, branding, security rules, backup and restore, data retention and an audit log.
- **Sign-in protection**: optional two-factor authentication (authenticator app or emailed code), lockout after failed attempts, and session limits.

## Requirements

- Node.js 20 or newer
- PostgreSQL 14 or newer
- nginx (or another reverse proxy) for HTTPS in production

## Run locally

```bash
cp .env.example .env     # fill in the values described inside the file
npm install
npm run build            # builds the front end
npm start                # creates the tables and the first Admin on first start
```

For front-end development, run `npm start` and `npm run dev:client` in two terminals.

## Deploy

1. **Get the code** onto the server and install: `npm ci --omit=dev`, then `npm run build`. (You can build on another machine and copy `client/dist/`.)
2. **Configure**: copy `.env.example` to `.env`, fill in every required value, and restrict the file (`chmod 600 .env`).
3. **Database**: create an empty PostgreSQL database and a login for the app, then point the app at it (see below). Tables are created on first start.
4. **Run as a service**: use the example unit in `deploy/` with systemd, then enable and start it.
5. **HTTPS**: put nginx in front using the example in `deploy/`, and set `TRUST_PROXY` and `APP_ORIGIN` in `.env` as described in `.env.example`.
6. **First sign-in**: sign in with the seeded Admin, choose a new password, then set up groups, users and dropdown lists in Administration.

**Upgrading**: pull the new code, run `npm install --omit=dev` and `npm run build`, then restart the service. Run `npm install` again whenever `package.json` changes.

## Connect to the database

1. Create a database and a login (run as the PostgreSQL admin, and choose your own strong password):

   ```bash
   sudo -u postgres psql -c "CREATE ROLE hub_user LOGIN PASSWORD 'choose-a-strong-password';"
   sudo -u postgres psql -c "CREATE DATABASE hub OWNER hub_user;"
   ```

2. Put the connection string in `.env`:

   ```
   DATABASE_URL=postgresql://hub_user:choose-a-strong-password@localhost:5432/hub
   ```

   If the password contains special characters such as `@` or `#`, URL-encode them. Set `PGSSL=true` if the database is on another server and requires TLS.
3. Start the app. It connects and creates its tables automatically. If it cannot connect, the log (`journalctl -u <service-name> -n 30`) names the problem.
4. To check the connection by hand: `psql "$DATABASE_URL" -c "select 1"`.

## Maintenance mode

Closes the site to everyone except a System Admin, for upgrades and similar work. Everyone else sees an "Under maintenance" page, and their sign-in is refused with a message. The System Admin signs in as usual and sees a "Maintenance: ON" badge in the top bar.

- **In the app (no restart):** as a System Admin open Administration → Maintenance, optionally type a message, and press **Turn on maintenance mode** (and **Turn off** to end it). Every change is written to the Audit Log.
- **Flag file (no restart):** `sudo sh -c 'echo "Back at 3 PM" > /var/www/pcshub/MAINTENANCE'` turns it on; the text is the message shown. `sudo rm /var/www/pcshub/MAINTENANCE` turns it off. It takes effect within a second.
- **`.env` (restart needed):** set `MAINTENANCE_MODE=true` (and optionally `MAINTENANCE_MESSAGE`), then `sudo systemctl restart pcshub`. Set it back to `false` to end it.

Any one of the three being on is enough, so if it stays on after you turn it off in the app, check the flag file and `.env`. People already signed in are not signed out: they see the maintenance page until it ends, then carry on.

## Backup server (main + standby on the same LAN)

A second copy of the app that keeps itself up to date and takes over when the main server is gone. **Manual failover, up to `NODE_SYNC_HOURS` (default 4) of recent changes can be missing.**

How it works: the backup server is read-only. Every few hours it asks the main server for a fresh backup (the same archive as Administration → Backup and Restore: database, Branding and Knowledge files), downloads it, checks its checksum and restores it over itself. People can sign in on it with their normal accounts to read, nothing can be changed. When the main server is lost, a System Admin presses **Promote to main** (Administration → Backup Server) and users are pointed to it.

**Set up** (once):
1. Install the app on the second server like the first one: the same version (pull both together), the same PostgreSQL major version, `pg_dump` / `pg_restore` present, and `BACKUP_DATABASE_URL` set the same way as on the main server.
2. Copy `TOTP_ENC_KEY` (and `BACKUP_SIGNING_KEY` if you use it) from the main server's `.env`: 2FA secrets are encrypted with it, so the copied data is unreadable without the same key.
3. Make a shared secret (`openssl rand -hex 32`) and put it as `NODE_SYNC_TOKEN` in **both** `.env` files.
4. On the backup server also set `NODE_ROLE=backup`, `NODE_MAIN_URL=https://<the main server's address>` (the address the reverse proxy answers on; a self-signed certificate needs `NODE_EXTRA_CA_CERTS`) and, if you want, `NODE_SYNC_HOURS=4` (1 to 24).
5. Restart both. Within a minute the backup server makes its first copy; Administration → Backup Server shows when the data is from, when the next copy is, and whether the main server answers.

Not copied: `.env`, the backups folder and the Retention archives. The main server marks the backups it makes for the backup server "Backup server sync": they do not count against Backup Keep or the Backup limit, and only the newest is kept.

**To separate the two servers for good:** on the backup server open Administration → Backup Server → **Stop being a backup server…** (your password, type STANDALONE). It stops copying, becomes an ordinary main server on the data it has, and needs no check that the other server is down and no `.env` change (the saved role wins over `NODE_ROLE`; you can remove `NODE_ROLE`, `NODE_MAIN_URL` and `NODE_SYNC_TOKEN` from `.env` afterwards). The other server is not touched; from then on the two diverge.

**When the main server is down:**
1. Check it is really down (Backup Server tab → *Main server: Not answering*).
2. On the backup server: Administration → Backup Server → **Promote to main…** (your password, type PROMOTE). It refuses while the main server still answers, unless you tick the extra box.
3. Point users to the backup server (DNS name or the reverse proxy's address). It is now the main server and keeps that role across restarts (the role is stored in `<BACKUP_DIR>/node-state.json`, not in the database, because the database is replaced on every copy).

**When the old main server comes back:** do NOT start it as a main server, it holds old data. Before starting it set `NODE_ROLE=backup`, `NODE_MAIN_URL` (the new main server) and the same `NODE_SYNC_TOKEN` in its `.env`; if it was once promoted, delete its `node-state.json` or use *Make this a backup server…* on its Backup Server tab. It then copies the new main server and everything it held is replaced. To go back to the original layout later, promote it the same way and make the other one a backup server.

### App name

The name set in Administration → Branding is used everywhere, including the places the browser reads before the app loads: the tab title, the installed-app (PWA) name and home-screen label (`/manifest.webmanifest` is generated from it; the label is the name cut to about 12 characters at a word boundary), and the offline page.
